# 方法论（Metamethodology）

> 每条都来自真实故障，且都能配一个具体的「现象 → 诊断 → 根因 → 修复 → 复盘」故事。
> 用法：**动手前扫一眼，收尾前对一遍**。故事见 [`incidents/`](incidents/)，本文只保留规则本身。

## 两条元规则

> **每次改完先问一句「我怎么知道它生效了」，然后找一个能证明的观测点。**

> **幂等能保证系统稳定，不能保证系统正确——收敛性验收与正确性验收，缺一不可。**

---

## ① 文件内容 ≠ 实际生效值

- 来源：`sshd_config` 里写了 `X11Forwarding no`，`sshd -T` 仍显示 yes（lineinfile 替换了最后一条匹配行）。
- 延伸：`nginx -T` 显示新配置 ≠ 运行中的 master 已加载它（它只是"读磁盘解析并打印"）。
- 做法：验收一律打**生效值**——`sshd -T` / `nginx -t` / 业务请求的真实响应，而不是看文件内容。

## ② `--check` 不是幂等测试

- 来源：`--check` 不写任何文件，跑几次结果都一样，无法暴露"第二次是否收敛"。
- 做法：实跑（`changed=N`）→ 再跑（期望 `changed=0`）。base / security / web 三个角色均以此方式验收。

## ③ 验证「关闭类」改动必须配对照组

- 来源：验证 `access_log off` 时，只看到"日志零增长"不足以定论——也可能是日志整体坏了。
- 做法：**同时**发起正常请求（`/` 返回 200、`/nonexistent-404-test` 返回 404）确认日志仍在写，
  再做跨周期增量对比。单次快照无法证明**周期性**行为。

## ④ 相关性 ≠ 因果

- 来源：09-12 改完 MTU 后推送立刻成功，被记为"修复有效"；09-24 复发时同样的改动**完全无效**，
  而切换到手机热点立刻稳定。
- 做法：归因必须靠**重复验证或对照**——同一网络换目标主机对照，或同一目标换网络对照。
- 附带：**没有实测收益的配置不要持久化**，否则会留下无法解释的"迷信配置"。

## ⑤ 修复要考虑路径依赖（多路径择优）

- 来源：同一目标存在多条可达路径，稳定性差异巨大：

  | 路径 | 稳定性 |
  |---|---|
  | 本机 → GitHub | 不稳定（间歇性挂起、无输出） |
  | 本机 → 阿里云服务器 | 稳定 |
  | 阿里云服务器 → GitHub | 稳定 |

- 做法：**绕开不稳定段**——用服务器做同步中转，把"本机 → GitHub"拆成两段稳定链路。

## ⑥ 幂等 ≠ 正确（`changed=0` 只证明收敛，不证明状态正确）

- 来源：2026-09-26，IaC 侧一份过期的 `default.conf` 覆盖了服务器上已修好的配置，容器转为 unhealthy；
  **修复前的第二次运行 playbook 报 `changed=0`，但系统是坏的**。
- 机制：`changed=0` 是相对于 **IaC 里声明的期望状态**收敛的。当期望状态本身是错的副本时，
  幂等检查会毫发无伤地把这个错误状态一直维持下去。
- 推论：
  - 幂等只保证"不再漂移"，不保证"漂向的地方是对的"；
  - **多真源 = 迟早互相覆盖**：同一份配置只允许存在一个源头；
  - IaC 的"期望状态"必须与真源一致，而不是与"另一份副本"一致。
- 做法：幂等验收之外**必须再加一次业务层验收**（`docker inspect` 的 Health、真实 HTTP 响应、业务返回码）。

## ⑦ 告警三视图 ≠ 一个真源

- 来源：2026-10-09，vmalert `/api/v1/alerts` 已 firing，但 VM `ALERTS` 恒空、alertmanager 根本不存在。
- 三个视图是**三条独立链路**：
  - 引擎态 = vmalert 内存里的规则状态；
  - 落库态 = 经 `--remoteWrite.url` 写进 VM 的副本；
  - 送达态 = 经 `--notifier.url` 转发到 alertmanager 的结果。
- 做法：验收告警必须**三点同验**，缺一不可。只看一个视图 = silent alarm 的温床。
- 自检：`docker inspect vmalert --format '{{.Config.Cmd}}'` 里**必须同时出现**
  `--datasource.url`、`--notifier.url`、`--remoteWrite.url`。

## ⑧ 部署路径 / 流程无约束 = 隐性真源泄漏

- 来源：2026-10-09，文档写 `/root/sre-lab`，实际在 `/opt/sre-lab`；
  observability 不在 Ansible 内（`site.yml` 只有 base/security/web），靠手工 `git pull` 维系。
- 做法：**路径与部署方式必须写进 README 并被 IaC 或脚本强制**，不能只靠人的记忆。
- 推论：「文档路径 ≠ 实际路径」本身就是故障源——下次照文档操作会找不到文件。

## ⑨ 判据必须能区分失败原因

- 来源：`docker compose config >/dev/null && echo OK || echo 语法错`，
  在**没装 docker 的控制机**上跑，把「命令不存在」误报成「语法错」——一个假阴性。
- 做法：判据先做环境检查，把"环境缺失"与"真实失败"分开：

  ```sh
  command -v docker >/dev/null || { echo "环境缺 docker，跳过"; exit 2; }
  ```

- 推论：`A && echo OK || echo FAIL` 是坏模式，会把多种失败混成一种结论。

## ⑩ 验证手段必须先于被验证对象可用

- 来源：2026-09-26，想用 playbook 里的 `assert` 拦住"目标机 Python 损坏"——
  但 `assert` 本身也是模块，同样依赖目标机 Python，而 Python 恰恰是坏掉的那一环。
- 做法：设计校验时，先确认**校验手段自己能不能跑起来**。

## ⑪ 改了被挂载的配置 ≠ 容器生效（`up -d` 是 no-op）

- **来源①**：2026-10-09，把 alertmanager 的 receiver 从 webhook 换成 SMTP 后跑 `docker compose up -d`，
  **容器根本没重建**，仍在跑旧配置（日志里还是 `integration=webhook[0]`）；直到加 `--force-recreate` 才生效。
- **来源②（次日即复现）**：2026-10-10，为了验证告警规则，临时把 `alert-rules.yml` 的阈值压低、`for` 改成 `0s`，
  `git pull` + `up -d vmalert` 之后 —— 文件里三条规则明明是新阈值，
  **vmalert 加载的却还是前一天的旧值**，结果是「告警邮件一封都没收到」。
- 机制有三层，都得知道：
  - **compose 层**：`up -d` 只比较**服务定义**（image/command/ports…），**不比较挂载文件的内容** → 判定"无需变更"；
  - **Docker 层**：`cp` 或编辑器覆盖文件会**换 inode**，旧容器的 bind-mount 仍指向**旧 inode** → 连 `restart` 也不管用；
  - **热重载层**（来源②暴露）：**即使程序支持热重载，也未必救得回来**。inotify 盯的是 **inode**，
    而 `git pull` / `cp` / 编辑器写入都是 **rename 替换**文件 → 监视对象消失 → 不会触发重载。
    **不要把"它有热重载"当成兜底。**
- 做法：**只要改的是被挂载的配置文件，一律 `docker compose up -d --force-recreate <svc>`**。
- **判据要求（关键）**：对"加载型"组件，验收必须打**它自己报告的生效值**，而不是 `grep` 文件内容：

| 组件 | 生效值怎么看 |
|---|---|
| vmalert | `curl -s 127.0.0.1:8880/api/v1/rules` → 看 `query` 与 `duration` |
| nginx | `nginx -t`（注意 `nginx -T` 只是读盘解析并打印，**不等于运行态**） |
| sshd | `sshd -T` |
| 任意容器读到的配置 | `docker exec <svc> cat <容器内路径>` |

- 同族：① 在**配置解析层**，本条在**挂载 / 加载层**——同一个病，换了个器官。
  两天内三次复现（09-24 nginx 未 reload、10-09 alertmanager、10-10 vmalert），说明它不是偶发，而是**默认会发生的**。

## ⑫ 收紧权限前，先确认「谁要读它」

- 来源：2026-10-09，为保护 SMTP 授权码给 alertmanager 配置 `chmod 600`，
  结果容器 crash loop —— 镜像以 **`nobody`** 运行，读不到 root 私有的文件
  （`error loading configuration file: ... permission denied`）。
- 机制：`600 + root:root` 对**非 root 的消费进程**等于"文件不存在"。
- 做法：
  - 先查消费方身份：`docker inspect <c> --format '{{.Config.User}}'`；
  - 判据必须取**消费方视角**：`docker exec <c> cat <路径>`，
    而不是在宿主用 `sudo -u nobody cat <宿主机路径>`（会被目录权限挡住，产生**假阴性**）。
- 附带结论：**"更严的权限"未必"更安全"**。600 挡不住宿主 root / docker 组（他们等效 root），
  而它唯一多挡的"未来可能出现的第二个容器内身份"当前并不存在。
  **真正的边界是：文件不入库 + 目录不可穿越 + 容器不持有宿主能力。**
  详见 [ADR 0002](adr/0002-secret-file-permissions.md)。

## ⑬ 回滚 / 还原必须以「显式标识」为目标，不能用相对引用

- 来源：2026-10-10，Phase C 还原临时阈值时，手册写的是 `git revert --no-edit HEAD`。
  但那条测试提交（`68180cc`）之后**又叠了一条文档补丁提交**（`79a203e`）——
  此时 `HEAD` 已经是文档提交，`revert HEAD` 会去**还原文档**，而阈值一动不动。
- 机制：`HEAD` / `HEAD~1` / `HEAD^` 是**相对引用**，指向的是「**当前**位置」。
  只要在目标提交之后又产生了任何提交，相对引用指向的就**不再是**原来那条。
- **为什么危险：这类错位是静默的。**
  - 撤销一个文档改动，你几乎不会立刻发现；
  - 而真正该撤的临时配置（被压低的告警阈值）留在生产里，从此疯狂误报或误导判断。
    比"命令直接报错"危险得多 —— 报错会打断你，错位只会让你以为成功了。
- 做法（四步，缺一不可）：
  1. **先定位**：`git log --oneline -N` 找到目标提交的 **SHA**；
  2. **动手前复核**：`git show --stat <SHA>` —— 确认它改的文件就是你打算动的那个；
  3. **用显式 SHA**：`git revert --no-edit <SHA>`（或 `git checkout <SHA> -- <path>`）；
  4. **还原后验生效值**，而不是只验"命令没报错"。
- 推论：**凡是「撤销 / 回退 / 回滚」类操作，目标都必须能被独立指认**
  （SHA、时间戳、明确路径）。依赖"当前位置"的写法，只在
  「我是唯一操作者 且 期间没有任何新提交」时才成立 —— 而这两条前提都不该假设。
- 同族：①（打生效值，不看文件内容）、⑫（判据从消费方视角取）——
  都属于「**别对着代理指标下手**」。

## ⑭ 迁移 / 拷贝不保留权限语义；而工具可能把权限当安全前提，然后静默降级

- 来源：2026-10-14，控制端迁移后 `ansible lab -m ping` **不报错、也不生效**。三条 WARNING 说穿了全部真相：
  `ignoring it as an ansible.cfg source` / `No inventory was parsed` / `Could not match supplied host pattern, ignoring: lab`。
- 机制：文件经 `/mnt/c`（DrvFs / NTFS）中转进入 WSL，**这一路没有 `tar -p` 式的权限保留**，
  整棵树按挂载默认值落盘 = `0777`（实测 135 目录 + 150 文件，连 `.git/objects/` 都是）。
  而 Ansible 的设计是：**从全局可写目录加载 `ansible.cfg`，等于把 `roles_path` 交给任何能写该目录的人**
  → 它宁可**不读配置**。这是**正确的**安全设计，不是 bug。
- **最危险的部分是"没有报错"**：
  - `exit code = 0`；
  - `--syntax-check` 照样通过（它不依赖 inventory）；
  - `ansible-playbook site.yml` 以 `skipping: no hosts matched` 优雅结束。
  复盘时极易读成"跑完了，没事" —— 这是**安静的成功**。
- 做法：
  - 迁移 / 解包 / 跨文件系统拷贝之后，**权限必须显式重建**：
    `find <dir> -perm -o+w | wc -l` 应为 0，不对就 `chmod -R go-w <dir>`；
  - 别假设拷贝工具保留了权限位 —— `zip`、无 `-p` 的 `cp`、DrvFs 都不保留。
- 推论：**「没报错」不是验收判据。** 与 ① 同族但层次不同 ——
  ① 是「文件内容 ≠ 生效值」，本条是「**配置根本没被加载**」。
  验收一律打生效值：`ansible --version` 的 `config file` 指向、`ping` 的 `pong`、实跑的 `changed=N`。
- 附带（工具链版本同理）：`ansible-core` 也随控制端重建而漂移，
  **控制端 Python 版本决定能装的 ansible-core 上限**（≥2.18 要求 Python ≥3.11）——
  重建后必须重新确认，不能照抄旧记录。

## ⑮ 增量式 IaC 不会纠正漂移，只会忽略它

- 来源：2026-10-14，服务器 `trusted` 区多出一条 IaC 之外的规则 `192.168.0.0/16`，
  是 09-16 手工所加、**游离 28 天无人发现**。
- 机制：`security` 角色的 firewalld 任务是**增量式**的 —— 先 `--query-*` 问在不在，
  不在才 `--add-*`，**从不删除、从不重置**。于是**方向决定了命运**：

  | 在服务器上做的动作 | playbook 的反应 | 症状 |
  |---|---|---|
  | **加**一条新规则 | **不撤销**（只问 IaC 声明的那几条） | `changed=0`、无警告 → **失败只在重建那天暴露** |
  | **删** IaC 里已有的条目 | 下次跑会**加回来**（真源获胜） | "我改的东西自己变回来了" |

- 这类工具的**正确性判据是「我声明的都在」，不是「实际的都归我管」**。
  漏报（多余项不被发现）不会打断你，只会让真源悄悄变成两个 ——
  与 ⑭ 同属"**不报错的失败**"，但层次不同：⑭ 是配置没被加载，本条是**工具的设计边界**。
- 做法：
  - 需要"机器上没有多余项"时，必须**单独写判据**。
    本例用的是系统自带的双目录基线（无需维护白名单）：
    `/usr/lib/firewalld/zones/*.xml`（RPM 出厂态）→ `/etc/firewalld/zones/*.xml`（当前态）
    的全部差异，减去 IaC 声明 = 无主改动；
  - **手工改动回填 IaC 必须做差集核对**，不能凭记忆 —— 手改 N 条、回填 N−1 条是常态；
  - 验证"IaC 真能重建"的唯一办法是**先删后建**（或干净环境）。
    先手工加、再补进 IaC，只会得到 `changed=0`，**什么都证明不了**。
- 推论：**风险大小取决于有没有消费方，不取决于在不在 IaC 里。**
  本例那条规则无消费方（conntrack 实测 0 条流量），丢了也不出事，属审计问题；
  而 k3s 的网段规则有消费方，丢了就是功能事故。

## ⑯ 判据的数据来源本身也可能是假的（缓存 / 索引 / 被裁剪的输出）

- 来源：2026-10-14 一天之内三次，全部发生在**验证环节**，没有一次是"配置写错了"：
  1. `core.fileMode=false` → 磁盘权限 `755` 是对的，但**索引里记的是 `644`**；
     而**会被重建的是索引那一份** → 新机器上脚本不可执行；
  2. `origin/main` 只是**本地缓存**，`git fetch` 失败时不报错只留旧值
     → 被读成"GitHub 落后"（同类假信号累计出现 **3 次**）；
  3. 核验命令里的 `2>/dev/null` **把"fetch 失败"这个词吞掉了** → 过期缓存被当成事实。
- 机制：我们看到的几乎都是**事实的代理**。代理会**过期**（缓存）、会**漏记**（索引）、
  会**被自己裁掉**（重定向）。**"我查过了" 与 "我查的是事实" 是两件事。**
- 做法：对每个验证值问一句 —— **"这是事实，还是事实的代理？"**

  | 我看到的 | 它其实是 | 事实是 |
  |---|---|---|
  | 磁盘上的文件权限 | 代理（本地状态） | **索引里记录的模式**；重建后用 `git clone` 实测 |
  | `origin/main` | 代理（缓存） | **`git ls-remote`** 的实时结果；或钩子日志里 push 被接受的那行 |
  | 命令的退出码 | 代理 | **它的 stderr** 才说明为什么 —— **绝不吞 stderr** |
  | 校验器的 `exit=0` | 代理 | 它**对已知错误输入也会失败**这一事实 |

- **校验器本身也要验**：拿一个已知错误的输入喂给它，确认它真的会失败。
  （实测：`alloy fmt` 对写坏的配置也返回 `0`，真正的校验器是 `alloy validate`。）
  一个永远输出"通过"的检查器毫无价值。
- 同族：①（打生效值，不看文件内容）、⑨（判据要能区分失败原因）、
  ⑫（判据从消费方视角取）、⑬（别用相对引用）—— 都属于「**别对着代理指标下手**」。

## ⑰ 稳态、瞬态、累计量，不能混用同一把尺子

同一个事实，在不同时点采样会得到**不同的结论**，而三种量各有各的正确用法：

| 想回答的问题 | 该用什么 | 不能用什么 |
|---|---|---|
| **现在有没有危险** | 两个时点的**差分**（`memory.current` 前后各一次） | 单次快照 |
| **故障规模有多大** | **不回退的计数器**（journald 行数、启动次数） | 会被修复动作重置的指标 |
| **历史上最高到过多少** | 内核支持的水位线（`memory.peak`，5.19+） | 5.10 上**根本没有**这个文件 |

三次实证：

- **k3s 控制面**：崩溃循环中读到 `329.5 MiB`，稳定后是 `558 MiB` —— **差 70%**。
  崩溃中的数字不是"开销"，是"第 N 次启动到校验失败那一刻的瞬时值"。
- **`alloy` 的 `memory.events.max = 783`**：单看像"正在被限流"，跨周期观测 `Δ=0` ——
  实际是启动回灌期的一次性事件（旁证：`loki_write_dropped_entries_total` 五种 reason 全 0）。
- **ArgoCD 的 `available`**：354（拉镜像中）→ 459（空转）→ 354（有负载）。
  **"装完测一次"既不保证是峰值，也不保证是稳态。**

**动作**：报数字之前先问一句 —— **我这次测的是稳态、瞬态，还是累计量？**
判据选错，结论就会在"太乐观"和"太悲观"之间随机跳。

## ⑱ 探活接口通过，不代表你的用途可行

`GET /v2/` 是 registry 的**探活**接口；拉镜像是 **blob** 路径。两者会给出**相反的结论**：

| mirror | `/v2/` | 能不能下 blob |
|---|---|---|
| `docker.m.daocloud.io` | 401（正常） | ❌ 502 |
| `dockerproxy.net` | **502** | ✅ 7/7 层，32.9 MB |

只看探活，两个都判反了。同族的例子还有一堆：

- `systemctl is-active` = `active`，但服务在无限重启（`activating` 循环）
- `/healthz` 返回 200，但业务接口全 500
- `helm list` **默认隐藏 `failed` 的 release**（要看 `--all`）
- `ansible-playbook --syntax-check` 通过，但 inventory 根本没加载

**动作**：判据必须**真的走一遍业务路径**（真的下一层 blob、真的调一次业务接口、
真的跑一次 playbook），而不是打一个"我还活着"的接口。

```
同族：⑯（判据的数据来源本身也可能是假的）
区别：⑯ 是"你拿到的数据过期/被裁剪了"；⑱ 是"你问的问题不是你想问的那个"。
```
