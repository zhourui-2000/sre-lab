## 1. 为什么要有 SLO（而不是"看面板"）

面板回答的是「现在怎么样」。SLO 回答的是「这个月还能坏多久」。

这两件事的差别不是措辞，是**决策方式**：

| 只有指标 | 有 SLO |
|---|---|
| 可用性 99.9%，好还是不好？没人知道 | 99.9% 对 99.5% 的目标 = 还剩 4/5 预算，可以放心变更 |
| 每次抖动都要人判断要不要处理 | 烧钱率决定**要不要叫醒人**，而不是每条告警都叫 |
| 想加功能 vs 想稳，靠吵架 | 预算还有余额 → 允许冒险；预算烧光 → 冻结变更，先还债 |

对一台 2C2G 的单机实验环境，SLO 的真正价值是**练习这套决策流程**，
而不是追求一个漂亮的数字。

## 2. SLI 定义（口径只有这一份）

```
SLI = 30 天内 probe_success 的平均值
    = 成功探测次数 / 有效探测次数
```

| 项 | 取值 | 为什么是这个 |
|---|---|---|
| 探针 | `blackbox-exporter v0.29.0`（docker compose） | 见 ADR 0005：不进 k8s |
| 目标 | `https://zhourui2000.online/healthz` | **只测规范化后的入口**。www 与 http 是跳转层，它们"正确"的结果是 301，混进 SLI 会让口径自相矛盾 |
| 判定 | HTTP **严格 200**，`follow_redirects: false` | "跟随之后是 200"会把跳转配置的错掩盖成"能用" |
| 间隔 | **15s** | 30 天 ≈ 17.3 万次样本；再密只会增加噪声存储，不会提高判断力 |
| 窗口 | **30 天滚动** | 够长能吸收抖动，够短能反映近期质量 |
| 数据源 | `probe_success{job="blackbox"}` | **唯一**一个 job 参与 SLI（见不变量） |

**其他入口不参与 SLI，只做"存在性"检查**：`job="blackbox_follow"` 覆盖
`https://www…/healthz`、`http://…/healthz`、`https://…/`，它们掉了我需要知道，
但它们的状态不该让"可用性"这个数字变模糊。

## 3. SLO 与错误预算

| 项 | 值 |
|---|---|
| SLO | **99.5% / 30 天滚动** |
| 错误预算 | 0.5% |
| 折算 | 30 × 1440 × 0.5% = **216 分钟** ≈ 3 小时 36 分 |
| 折算（次数） | 216 分钟 ÷ 15s = **864 次**失败探测 |

**为什么是 99.5% 而不是 99.9%**：

- 99.9% = 每月 43 分钟。这台机器要跑 k3s + ArgoCD + 8 个容器，
  一次 `docker compose up -d` 滚动重建、一次内核重启、一次证书续期演练
  都能吃掉大半。定一个注定烧光的 SLO，结果是**大家学会忽略告警**——那比没有 SLO 更糟。
- 99.5% 的余量够做**变更**（这正是错误预算的用途：花它，而不是供着它）。
- 这个目标**没有历史数据支撑**，是初始值。第一个 30 天窗口结束后按实际分布复核，
  写在 `capacity.md` 的复盘里。

## 4. 烧钱率与告警分层

```
烧钱率 = 当前错误率 ÷ (1 − SLO) = 当前错误率 ÷ 0.005
```

1× = 按此速率恰好在 30 天里用完预算；14.4× = 1 小时烧掉 2% 预算。

| 告警 | 长窗口 | 短窗口 | 阈值 | 资源消耗 | severity | 该做什么 |
|---|---|---|---|---|---|---|
| `SloFastBurn` | 1h | 5m | 14.4× | 2% / 1h | critical | 立刻处理，别等 |
| `SloMediumBurn` | 6h | 30m | 6× | 5% / 6h | warning | 本班次内处理 |
| `SloSlowBurn` | 3d | 6h | 1× | 10% / 3d | info | 排期处理 |

**为什么要两个窗口同时成立**：长窗口判"严重程度"，短窗口判"是否还在烧"。
只有长窗口时，故障修好了告警还会挂很久（误报）；只有短窗口时，一次抖动就触发（噪声）。
两个都成立才是"确实在持续烧钱"。

**烧钱率的真正作用是替代"每次都叫醒人"**：`SiteDown` 保留，但它只覆盖
"探针明确看到失败"这一种。短暂抖动、间歇失败、慢速劣化，`SiteDown` 全都看不见——它们只能靠烧钱率。

## 5. 探针挂了 ≠ 站点挂了（这套规则最容易做错的地方）

`avg_over_time` **会跳过没有样本的时间段**。所以：

| 实际情况 | `probe_success` | SLI 显示 | 正确的告警 |
|---|---|---|---|
| 一切正常 | 全 1 | 100% | 无 |
| 站点真的坏了 | 全 0 | 掉到 0% | `SiteDown` + 烧钱率 |
| **探针/采集链路坏了** | **没有样本** | **停在最后一个值（看起来还很好）** | `ProbePipelineDown` / `SloNoData` |
| blackbox 活着但没产出数据 | 没有样本 | 同上 | `SloNoData` |

第三行是这套体系最反直觉的地方：**监控自己坏掉时，仪表盘最平静。**
所以必须有一条告警不依赖 SLI 的分母，直接看 `up{job=~"blackbox.*"}` 与样本数。

> 这是方法论 ⑯ 的一种具体形态：判据的数据来源本身可能是假的。
> 这里的假信号不是"缓存/代理"，而是**空洞**。

## 6. 测量点偏差（必须写清，否则会被读成"外网可用"）

探针跑在服务器上，从 ECS 拨自己的公网域名 —— 依赖 **hairpin NAT**。
2026-10-17 已实测这条路通（服务器拨自己域名返回 301 / 0.090s，与外部一致）。

它**能**证明：nginx 活着、TLS 能握手、路由与 location 配置正确、证书链完整。

它**不能**证明：

- 公网 DNS 解析正常（探针直接用域名，但走的是同一台机器的 resolver 缓存）
- 外部链路可达（运营商、跨境、CDN 段）
- 安全组 / ACL 没有只拦外部流量（hairpin 可能不走同一套规则）

→ 结论：**这是一个"服务内部可用性"SLI，不是"端到端可用性"SLI。**
要拿到真正的外部视角，需要一台外部探针（例如 GitHub Actions 定时 curl 后
把结果推进 VM）。这件事不在本轮范围，记在 `baseline.md` 的待补基线里。

## 7. 证书为什么不在 SLI 里

`blackbox.yml` 里两个模块都是 `insecure_skip_verify: true`（只跳过校验，
仍然会解析叶子证书，所以 `probe_ssl_earliest_cert_expiry` 照样可用）。

理由：证书过期和服务不可用是**两种故障**，混在一个 `probe_success` 里会互相掩盖：

- 证书过期但服务正常 → 被算成"站点挂了" → 告警指向错误的方向
- 服务真挂了但证书也快过期 → 两条告警同时响 → 分不清主因

所以证书单独一条 `CertExpiringSoon`（21 天），因为它**不需要**进错误预算：
证书问题没有"部分用户受影响"这种灰度，只有"到时候全挂"。

## 8. 未证事项（别把设计当结论）

- **`SiteDown` 的"红"只做过逻辑证明**（用一个必然 404 的 URL 手工打探针，
  确认 `probe_success` 会变 0），**没有真的停过站**去观察告警。
- `ProbePipelineDown` 会做一次真实演练（停 blackbox 4 分钟），因为它的代价是零
  —— 站点不受影响，正好用来验证"探针挂了 SLI 不动"这件事。
- 99.5% 目标没有历史数据支撑。
- 30 天窗口的 `avg_over_time` 在第 1 天只覆盖已有数据，**前 30 天的 SLI 是"到目前为止"的**，
  不是完整窗口的。

## 10. 启动期的两个现象（2026-10-19 首次落地实测）

这两件事都不是故障，但都会让"刚接完监控"的人误判成故障。记在这里，下次别再查一遍。

### 10.1 窗口没填满 ≠ 采集有洞

刚建立 5 分钟的序列，`count_over_time(probe_success[15m])` 只能是 ~20 个样本，不是 60。
**判据要拿同期 `up` 的样本数当基准**（同一 job、同一间隔），而不是拍一个固定值。

实测佐证：报告显示"23 个样本"时，同期 `up` 是 30 个 —— 两者几乎相等，说明**没有洞**，
只是序列才存在 7 分钟。判据错在基准，不在数据。

### 10.2 记录规则互相引用会逐层晚一个周期

`count_over_time(<recorded_series>[2h])` 的实测值：

| 规则 | 样本数 | 含义 |
|---|---|---|
| `slo:sli_ratio:30d` | 6 | 第一层 |
| `slo:error_ratio:30d` | 5 | 引用上面 → **晚 60s** |
| `slo:error_budget_remaining:ratio` | 4 | 再引用 → **再晚 60s** |
| `slo:error_budget_remaining:minutes` | 3 | 再引用 → **再晚 60s** |

链式三跳 = 约 3 分钟。vmalert 重启后那 3 分钟里，"错误预算"面板是 No data ——
而重启后恰恰是有人盯盘的时刻。v2 已把这三条改成**全部直接从 `probe_success` 计算**，
启动后 1 个周期内就位。

> 代价：`avg_over_time(probe_success[30d])` 被算 3 次而不是 1 次。
> 一条序列 × 每 60 秒 —— 可以忽略。用 3 分钟的面板空窗去换，不值。

### 10.3 演练实测：把探针停 13 分钟（2026-10-19）

这是这套 SLO 唯一能**安全制造**的故障：站点完全不受影响，但监控链路断了。

| 时刻 | 事件 |
|---|---|
| T | `docker stop blackbox` |
| T + ≤30s | VM 抓取失败，开始写 `up = 0`（`probe_success` 则**停止出现**） |
| T + 4m | 告警状态 = **pending** —— `for: 3m` 的 3 分钟**不是从 stop 算起**，前面还有两段延迟 |
| T + 4m15s | 转 **firing** |

**`for:` 的真实时间账**：

```
停容器 → VM 下次抓取失败才写 up=0     ≤ 15s（follow job 30s → ≤30s）
        → vmalert 下一轮评估才进 pending  ≤ 60s
        → 再连续 pending 满 3 分钟        180s
                                          ─────
                                      最多 255s
```

**停摆第 9 分钟时的实测：整套 SLO 面板全绿。**

| 指标 | 值 |
|---|---|
| SLI / 错误预算剩余 | `1` / `1`（100% / 100%） |
| 烧钱率 5m / 1h | `0` / `0`（5m 的记录规则甚至停止产出） |
| `SiteDown` | **0 条** —— 没有探针告诉它「失败了」 |
| `SloNoData` | **0 条** —— 要连续 15 分钟无样本才响 |
| `ProbePipelineDown` | **4 条 firing** |

→ **监控自己坏掉的时候，仪表盘最平静。** 这就是为什么必须有一条告警不依赖 SLI 的分母。

**告警状态机的一个坑**：`pending` 与 `firing` 是**两条独立序列**（`alertstate` 是标签），
不是同一个对象改字段；vmalert 停止写之后，VM 仍会把它保留到 lookback 结束（≈5 分钟）。
所以判断「已恢复」**不能看「查询结果为空」**，要数
`count(ALERTS{alertname=…,alertstate="firing"}) or vector(0)` 是否回到 0。
