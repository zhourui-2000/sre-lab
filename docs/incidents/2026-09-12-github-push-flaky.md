# GitHub 推送间歇性失败

- **日期**：2026-09-12 记录 / 2026-09-24 修正归因
- **影响**：`git push` 挂起且无输出，迭代中断
- **一句话结论**：公司网络到 GitHub 的链路不稳定（**不是** WSL 虚拟网卡故障）

## 现象

- `git push` 无限挂起、**无任何输出**
- `curl` 曾报 `Failed to connect ... after 7 ms`
- 间歇性发生；同一网络下浏览器访问 GitHub 正常

## 诊断与试错

| 措施 | 结果 |
|---|---|
| `wsl --shutdown` 重建网络栈 | 当时看似恢复 |
| `ip link set eth0 mtu 1400` | 当时看似恢复；09-24 复发时改 MTU **完全无效** |
| `ssh -o IPQoS=none` | 无效 |
| 改走 SSH 443（`ssh.github.com:443`） | ✅ 有效，已固化进 `~/.ssh/config` |
| **切换到手机热点** | ✅ **稳定推送** |

## 根因

**公司网络到 GitHub 的链路不稳定。** 同一网络下"本机 → 阿里云服务器"始终稳定，
说明问题出在"到 GitHub"这一段，而不是本地网络栈。

09-12 曾归因于"WSL 虚拟网卡故障"——那是**把相关性当成了因果**
（当时"改完立刻成功"更可能是链路自己恢复了）。

## 修复

- 推送前切手机热点；或使用**服务器中转链路**，见 [ADR 0001](../adr/0001-server-relay-push.md)

## 遗留

- 最初 `7 ms` 秒失败的成因仍未定论——按特征更像 hosts 劫持或代理端口未监听，而非链路超时

## 教训

- 见 [methodology ④](../methodology.md)：相关性 ≠ 因果
- 控制端与被管机分离后，**控制端可用性成为单点**，需有备用推送路径
