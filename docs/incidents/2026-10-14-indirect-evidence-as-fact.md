# 判据的数据来源也会骗人：三次「把代理当成了事实」

- **日期**：2026-10-14（一天之内三次）
- **影响**：三次都发生在**验证环节**，没有一次是"配置写错了"。
  其中一次差点让我们去修一个**不存在的问题**。
- **一句话结论**：**缓存、索引、被重定向裁剪掉的输出，都不是事实** ——
  它们只是事实的**代理**。而代理会过期、会漏记、会被自己裁掉。

## 案例 ①：磁盘权限对了，但「会被重建的那一份」没记

**现象**：新增 `scripts/check-fw-drift.py` 并提交，推送输出里写着 `create mode 100644` ——
可补丁脚本明明 `chmod 0755` 了，自检也报了 ✅。

**诊断**：

| 检查 | 值 |
|---|---|
| 磁盘上的权限 | `-rwxr-xr-x` `755` ✅ |
| git 索引里记录的模式 | `100644` ❌ |
| 控制端 `core.fileMode` | **false** ← 元凶 |
| 服务器上（对照） | `true` |
| 文件到服务器后 | `-rw-r--r--` `644` ❌ **可执行位已经丢了** |

**根因**：`core.fileMode=false` 时 git **完全忽略文件权限位**。
10-13 跨 `/mnt/c` 迁移时 git 检测到文件系统不可靠，自动关掉了这个开关 ——
与 [10-14 迁移权限事故](2026-10-14-migration-perms-ansible-cfg.md) 是**同一件事的两半**：
那半边是"拷贝丢掉权限语义"（`0777` 漂移），这半边是"**版本控制压根没记录权限**"。

**为什么危险：它在重建那天才发作。** 索引里是 `100644` → 新机器 `git clone` 出来就是 `644`
→ `./scripts/check-fw-drift.py` 报 `Permission denied`。
**"我磁盘上是对的"不等于"重建出来的机器上是对的"—— 会被重建的是索引里那一份。**

**修复**：`git config core.fileMode true` → 暴露出 3 个模式不一致的文件 → `git add` 提交。
（`methodology/runbook` 由 `755` 归正为 `644`，工具由 `644` 补为 `755`；随后又顺手归正了
迁移残留的另外 11 个 `.md`。现索引里 `100755` 只剩工具本身 1 个。）

**验证方式**：**直接做一次克隆**，检查克隆出来文件的磁盘权限：

```sh
git clone -q /root/sre-lab /tmp/clone-check
stat -c '%a' /tmp/clone-check/scripts/check-fw-drift.py   # 期望 755
```

**补记**：`git update-index --chmod=+x` 在 `fileMode=false` 下**仍然有效**
（已在对照仓库验证：索引立刻变 `100755`，克隆方拿到磁盘 `755`）。

## 案例 ②：`origin/main` 显示"落后"，而 GitHub 其实是最新的

**现象**：推送后做四端核验，输出 `origin : 828ca36`（旧），而 local / relay / server 都是新的 ——
看起来 GitHub 落后了。

**根因**：`origin/main` **只是本地缓存的远程跟踪引用**。
`git fetch` 失败时它**不报错、只保留旧值**。实测 `git fetch origin` 的报错是：

```
ssh: Could not resolve hostname ssh.github.com: Temporary failure in name resolution
```

（WSL2 的 DNS 间歇失败，已知问题，与配置无关。）

**而当时那条核验命令恰好把唯一的线索扔掉了**：

```sh
git fetch origin --prune 2>/dev/null; git rev-parse origin/main
#                          ^^^^^^^^^^^^^ 把"fetch 失败"这个词吞掉了
```

于是**过期缓存被当成了事实**。GitHub 实际早已最新，两处独立证据都指向同一结论：

- 中继钩子日志：`To github.com:zhourui-2000/sre-lab.git  <old>..<new>  main -> main`
  （git push 被远端接受后才会打印）；
- 从服务器侧直查：`git ls-remote origin main`。

**这个假信号已出现过三次**：`ahead 22` / `ahead 1` / `origin 落后`。

**修复**：判断远端状态一律**实时查询**，并明确标注本地引用"不作证据"：

```sh
git ls-remote origin refs/heads/main       # 实时（带 3–5 次重试）
tail -8 /var/log/sre-relay.log             # 或看钩子日志里 push 被接受的那行
```

已固化成工作区脚本 `check-three-ends.sh`：四方核验（local / relay / server / GitHub 实时）+
重试 + **实时查不到时用钩子日志兜底**（DNS 常年不稳，那行同样是硬证据）+ 退出码 `0/1`。

## 案例 ③：验证命令自己把唯一的证据裁掉了

案例 ② 里 `2>/dev/null` 是直接原因。**更一般地说：**

验证命令的职责就是**暴露失败**。把 stderr 吞掉之后，**失败会伪装成结论**。

- **失败会打断你；结论不会。** 它只会让你以为事情办好了 ——
  这正是它比报错危险的地方（同族：①③⑭⑮ 都是"不报错的失败"，但机制各不相同）。
- 做法：要么不重定向，要么 `2>&1 | tail -3`，要么在脚本里显式判断退出码。

## 同族补充（校验器本身也要验）

| 现象 | 机制 |
|---|---|
| `alloy fmt` 对**故意写坏**的配置也返回 `exit=0`（引用不存在的组件、时长格式非法都不报） | 它只是**格式化器**，不做语义校验。后改用 `alloy validate`（正例 `0`、两个对照组均 `1`） |
| 用 `inspect.signature(subprocess.run)` 判断参数是否存在，得到 `False` | `run` 的额外参数走 `**kwargs`，**这个判据本身是无效的**。真正的证据是"那段代码真的跑通了" |

**做法：拿一个已知错误的输入喂给校验器，确认它真的会失败。**
否则 `exit=0` 什么都说明不了 —— 一个永远输出"通过"的检查器毫无价值。

## 教训

- 方法论 [⑯](../methodology.md)：**判据的数据来源本身也可能是假的。**
- 通用问法：**"我手上这个值，是事实，还是事实的代理？"**

| 我看到的 | 它其实是 | 事实是 |
|---|---|---|
| 磁盘上的文件权限 | 代理（本地状态） | **索引里记录的模式** —— 那才是被重建的那份 |
| `origin/main` | 代理（缓存） | **`ls-remote` 的实时结果**；或钩子日志里 push 被接受的那行 |
| 命令的退出码 | 代理 | **它的 stderr** 才说明为什么 |
| 校验器的 `exit=0` | 代理 | 它**对已知错误输入也会失败**这一事实 |

- 与 [⑨](../methodology.md)（判据必须能区分失败原因）、
  [①](../methodology.md)（打生效值，不看文件内容）、
  [⑫](../methodology.md)（判据从消费方视角取）同族 ——
  都属于「**别对着代理指标下手**」。
