# 防火墙持久配置漂移：一条无主规则游离 28 天

- **日期**：2026-10-14（漂移产生于 2026-09-16 18:29:41）
- **影响**：服务器 `trusted` 区存在一条 IaC 之外的规则 `192.168.0.0/16`。
  **无功能影响**（该网段当前无任何匹配流量），但**重建机器时会静默丢失** ——
  并且暴露了一个机制性问题：**这台机器上防火墙的真源不止一个。**
- **一句话结论**：`security` 角色的 firewalld 任务是**增量式**的（只 `--add-*`、**从不删除**），
  所以服务器上手加的规则 playbook **既不会撤销、也不会报错** —— 漂移静默存活，直到重建那天。

## 现象与诊断

起因不是故障，而是一个提问：**"在服务器上改 firewall 规则，会不会破坏「主机配置即代码」？"**

诊断用的是 firewalld 自带的**双目录基线**（不需要维护任何白名单）：

```
/usr/lib/firewalld/zones/*.xml   RPM 出厂定义 —— 本地改动不写这个目录    ← 天然基线
/etc/firewalld/zones/*.xml       firewalld 只在本地有改动时才生成

全部本地改动     = 当前态 − 出厂态
无主改动（漂移） = 全部本地改动 − IaC 声明
```

逐条 diff 的结果：

```
--- public  ---  出厂态 → 当前态 差异 = 3 条  →  与 IaC 声明的 3 条 public 项完全吻合    ✅
--- trusted ---  出厂态 → 当前态 差异 = 2 条  →  IaC 只声明了 1 条                       ❌
                 > <source address="172.16.0.0/12"/>     ← IaC 有
                 > <source address="192.168.0.0/16"/>    ← IaC 没有 = 漂移
--- docker ---   /usr/lib 下无对应文件 → 由 docker 创建 = 运行时产物，不算漂移
```

**为什么不用白名单**：`public` 出厂自带 `ssh` / `dhcpv6-client` / `cockpit`。
靠白名单就得把它们写死，系统升级改了默认值就开始误报 ——
而**误报多了，人就学会忽略它**，判据也就废了。用 RPM 出厂文件做基线，永不腐化。

## 根因

两层，**都要修**。

### ① 机制层：增量式 IaC 不会纠正漂移，只会忽略它

`ansible/roles/security/tasks/main.yml` 的写法是"先 `--query-*` 问在不在，不在才 `--add-*`"，
**从不删除、从不重置**。于是同一个动作、方向不同，命运完全不同：

| 在服务器上做的动作 | playbook 的反应 | 症状 |
|---|---|---|
| **加**一条新规则 | **不撤销**（它只问 IaC 声明的那几条） | `changed=0`、无警告 → **失败只在重建那天暴露** |
| **删** IaC 里已有的条目 | 下次跑会**加回来**（真源获胜） | "我改的东西自己变回来了"（这其实是好事） |
| 只改 runtime、不带 `--permanent` | — | `reload` 或重启即消失 → 假象 |

这类工具的正确性判据是 **"我声明的都在"**，而不是 **"实际的都归我管"**。
危害形状：`exit code = 0` + 无警告。

### ② 过程层：回填 IaC 时凭记忆，没做差集核对

09-16 那次 firewalld 事故（见 [09-16 记录](2026-09-16-firewalld-blocks-scrape.md)）手工敲了两条：

```
/root/.bash_history:178,180   firewall-cmd --permanent --zone=trusted --add-source=172.16.0.0/12
/root/.bash_history:181       firewall-cmd --permanent --zone=trusted --add-source=192.168.0.0/16
/root/.bash_history:182       firewall-cmd --reload
```

回填 IaC 时**只回填了第一条**。`trusted.xml.old`（firewalld 改 `--permanent` 前自动保留的备份）
显示改动前只有 `172.16.0.0/12` —— 两条都是那天加的，**一条被记住、一条被忘掉**。

## 修复

**这一步必须手工做** —— 增量式 IaC 不会替你删除多余项：

```sh
firewall-cmd --permanent --zone=trusted --remove-source=192.168.0.0/16
firewall-cmd --reload
```

同时在 WSL 真源里把 k3s 需要的两条网段规则补进 IaC（`10.42.0.0/16` / `10.43.0.0/16`）。

**顺序是"先改 IaC，再让 playbook 去建"** —— 这样首次跑 playbook 会 `changed=2`，
就是「从无到有」的直接证明。若反过来（先手工加、再补进 IaC），playbook 查到已存在会报 `changed=0`，
**永远无法证明 IaC 真的能重建它**。

## 验证

新增 `scripts/check-fw-drift.py` 把上述判据固化成可复跑的命令
（退出码 `0` 干净 / `1` 有漂移或缺失 / `2` 工具自身前提失效）：

| 时点 | 结果 |
|---|---|
| 修复前 | `❌ 漂移 1 条`：`trusted source 192.168.0.0/16`，exit=1 |
| 删除后 | `✅ 完全一致（无漂移、无缺失）`，exit=0 |
| k3s 规则入 IaC 并 apply 后 | `IaC 声明 6 条` == `本地改动 6 条`，exit=0 |

工具本身也验过失败分支：用"真实文件 + 2 条规则"的假仓库构造缺失场景（正确报出 2 条缺失）、
指向不存在的仓库路径（exit=2，**不会静默通过**）。

**取证副产物**：删除后 `trusted.xml.old` 保存的正是 `2026-09-16 18:29:41` 的版本 ——
firewalld 自动把"漂移诞生那一刻"留了下来。
**`/etc/firewalld/zones/*.xml.old` 的 mtime，可以给任何非 IaC 改动定时。**

## 教训

- 方法论 [⑮](../methodology.md)：**增量式 IaC 不会纠正漂移，只会忽略它**。
- **手工改动回填 IaC 必须做差集核对**，不能凭记忆。手改 N 条、回填 N−1 条是常态，
  剩下的那条会安静地活到重建那天。
- 一次改动的**方向**决定了它的命运：在增量式 IaC 下，加与删的后果**相反** ——
  知道这一点，排查时能省掉大量猜测。
- **风险大小取决于有没有消费方，不取决于在不在 IaC 里。**
  本例这条规则无消费方（conntrack 实测 0 条流量），丢了也不出事，属**审计问题**；
  而 k3s 的两条网段规则有消费方（Pod/Service 网络），丢了就是**功能事故**。

## 遗留
