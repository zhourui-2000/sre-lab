## 1. 什么叫"恢复完成"

没有判据的 RTO 是个好看的空话。本项目把"恢复"拆成三级，**每级单独掐表**：

| 级别 | 判据（可执行） | 意味着什么 |
|---|---|---|
| **L1 内容可服务** | 从 GitHub 克隆后，`nginx` 用仓库里的 `html` 起得来，`/` 返回 200 | 站点**内容**能回来 |
| **L2 指标可采集** | 影子 VM 起来后 `up{job="node"} == 1`，且能查到 `node_*` 序列 | **可观测能力**能回来 |
| **L3 告警链可通** | 影子 vmalert 加载规则（`/api/v1/rules` 里看到组与条数） | **值班能力**能回来 |

**RTO 报告格式**：`L1 = N 秒（含克隆 M 秒）`、`L2 = N 秒`，并注明**是否含脚手架**。
含与不含要分开写 —— 否则数字会变成"最好看的那一个"。

## 2. RPO 按恢复单元定义

RPO 不是全局一个数，是**逐个单元**的。依据是"最后一次可靠的、可恢复的副本在哪"。

| 单元 | RPO | 依据 |
|---|---|---|
| 仓库内配置（compose / scrape / 规则 / .env / ArgoCD values） | **0** | GitHub，上次 push 之后 |
| 站点静态内容 | **不为 0，且大部分缺失** | `dtb/index.html`(29.6MB) 与 `story/index.html`(21.6MB) 被 `.gitignore` 排除 → 见 §4 |
| `/etc/rancher/k3s/*`、`/etc/docker/daemon.json`、`jail.local`、`99-sre-lab.conf` | **0** | Ansible 任务里的 `dest`，重跑 playbook 即还原（工具会打印匹配到的任务文件） |
| `/var/lib/rancher`（k3s 状态） | **无上限** | 无备份。配置类可经 ArgoCD 重建，**PV 数据不可** |
| `/etc/letsencrypt`（证书） | **无上限** | 无备份。可重签，但要 80 端口 + 域名解析 + 注意 rate limit |
| `/root/.sre-lab-secrets/alertmanager.yml`（含 SMTP 授权码） | **无上限** | 无备份，且不在库 —— **单点缺失** |
| `vmdata` / `loki-data` / `grafana-data` / `alertmanager-data` | **无上限** | 无备份。面板已 provisioning，但**历史数据与静默状态会丢** |

> 2026-10-19 盘点结果：**✅ 15 / ⚠️ 1 / ❌ 7**，四类备份目录**一个都不存在**。

## 3. 演练方法：影子重建

### 为什么用影子而不是真停

| 方式 | 站点影响 | 错误预算 | 结论可信度 |
|---|---|---|---|
| 真停生产再重建 | 中断 N 分钟 | **消耗**（5 分钟 ≈ 2.3%） | 最高 |
| **影子重建**（新目录 + 新端口 + 新项目名） | **零** | **零** | 略低（端口/证书用了脚手架，需单列） |

选影子的理由：**先把不确定性变成数字，再花预算去买确定性的收益。**

### 三条必须知道的坑

1. **compose 项目名默认取目录名** —— 影子目录若也叫 `nginx` / `observability`，
   `docker compose up` 会直接**接管生产容器**。必须显式 `-p shadow-web` / `-p shadow-obs`。
2. **`container_name` 是全局唯一的** —— 影子 compose 会撞名（`node-exporter` 已存在），
   必须 `sed -i '/container_name:/d'`。
3. **2G 内存跑不了两份全栈** —— 影子只能**逐组件串行**：起一个、验一个、拆一个。

### 脚手架与真实重建的差别（RTO 要注明）

| 项 | 影子演练 | 真实重建 |
|---|---|---|
| 端口 | 改到 8080 / 18428 / 19100 | 直接用 80 / 443 / 8428 |
| 证书 | **不重建**，L1 只验内容层 | 必须重签或从备份恢复 |
| 仓库来源 | GitHub（可用 relay 兜底，**要记录走了哪条**） | 同 |

## 4. 已发现的两个真源漏洞（2026-10-19）

### 4.1 站点 98% 的体积不在任何真源里

```
nginx/html 总 49M，其中：
  dtb/index.html    29.6 MB   ← .gitignore 排除
  story/index.html  21.6 MB   ← .gitignore 排除
  其余 4 个页面 + 2 个图片 + 1 个悬空软链   约 16 KB   ← 在库
```

`.gitignore` 里写着「大体积静态资源：待外置优化，暂不纳入版本控制」。
**后果：从 GitHub 重建出来的站点，首页能开，但 `/dtb/` 与 `/story/` 是 404。**

这条同时否掉了一个更早的判断：**"站点只有 6 个静态文件，用 ConfigMap 就够"** ——
① 文件数不等于字节数（6 个文件 49M）；② ConfigMap 单对象上限 1MB。
→ 站点要进 k8s，仍然需要一条**大文件分发通道**（镜像 / PVC + git-sync），
这件事**不会因为 GitOps 化而消失**。

### 4.2 密钥与数据：既不在库、也无备份

`/root/.sre-lab-secrets/alertmanager.yml` 只有一份，丢了就要重新申请 SMTP 授权码。
`/etc/letsencrypt` 同。这两项是 Week 7-B 的第一优先级。

## 6. 首次实测（2026-10-21）

影子重建，全程未碰 80/443，**错误预算消耗 0**。

| 项 | 表面值 | 内含 `sleep` | 净值 | 拆解 |
|---|---|---|---|---|
| L1 站点（内容） | 11 s | 3 s | **8 s** | 克隆 4 s + 起服务与验证 4 s |
| L2 指标（VM + NE） | 34 s | 25 s | **9 s** | 起服务到 `up=1` |
| 合计 | 45 s | 28 s | **17 s** | |

- **克隆走 GitHub 直连，4 秒**；`relay` 备用路径未触发（`dr.md` 第 3 节写的失败处置没用上）。
- **站点内容验证**：`/` 200、`/404.html` 200、**`/dtb/` 404、`/story/` 404** ——
  与 4.1 的盘点完全一致：那 49 MB 从来没进过仓库，所以"从 GitHub 重建"出来的站是个空壳。
- **`sleep` 必须扣**：`sleep 3` / `sleep 25` 是脚本在等，不是系统在恢复。
  不扣会把 RTO 虚报 **2.6 倍**（45 s vs 17 s），而且这个固定值会在跨次对比时淹没真实变化。

### 6.1 人工决策数：8 条（真实重建 4 条）

**命令条数不可比** —— 同一个 2.1，逐条敲是 9 条、整块粘贴是 1 次，差 9 倍而系统能力没变。
那个数只反映"打字方式"。改数**决策**：只数「换个人来做必须有人告诉他的信息」和
「做错不会自动纠正、必须人判断的地方」，纯搬运（`clone` / `docker run` / `curl`）一律 0 条。

| # | 决策点 | 真实重建需要 |
|---|---|---|
| 1 | 仓库地址 | ✅ |
| 2 | 站点根 `nginx/html` → 容器 `/usr/share/nginx/html` | ✅ |
| 3 | 镜像 `nginx:1.24-alpine` | ✅ |
| 4 | `/dtb/` `/story/` 的 404 是**预期**，不是故障 | ✅ |
| 5 | 8080 避让生产 80/443 | ❌ 影子特有 |
| 6 | 8428 / 9100 已被占，第二份要挪 | ❌ 影子特有 |
| 7 | `container_name` 全局唯一，第二份要删 | ❌ 影子特有 |
| 8 | compose 项目名默认取目录名，要 `-p` 隔离 | ❌ 影子特有 |

**真实重建只要 4 条** → 「重建动作」本身不难。**瓶颈不在操作步数，在内容分发**：
把 GitOps 化当解药，只会把一个"没有内容的站"搬进 k8s。

第 4 条是最贵的一种决策错误 —— 不知道这件事的人看到 404，会去修一个不存在的问题。
