## 1. 什么叫"恢复完成"

没有判据的 RTO 是个好看的空话。本项目把"恢复"拆成三级，**每级单独掐表**：

| 级别 | 判据（可执行） | 意味着什么 |
|---|---|---|
| **L1 内容可服务** | 从 GitHub 克隆后，`nginx` 用仓库里的 `html` 起得来，`/` 返回 200 | 站点**内容**能回来 |
| **L2 指标可采集** | 影子 VM 起来后 `up{job="node"} == 1`，且能查到 `node_*` 序列 | **可观测能力**能回来 |
| **L3 告警链可通** | 影子 vmalert 加载规则（`/api/v1/rules` 里看到组与条数） | **值班能力**能回来 |

**RTO 报告格式**：`L1 = N 秒（含克隆 M 秒）`、`L2 = N 秒`，并注明**是否含脚手架**。
含与不含要分开写 —— 否则数字会变成"最好看的那一个"。

## 2. RPO 按恢复单元定义

RPO 不是全局一个数，是**逐个单元**的。依据是"最后一次可靠的、可恢复的副本在哪"。

| 单元 | RPO | 依据 |
|---|---|---|
| 仓库内配置（compose / scrape / 规则 / .env / ArgoCD values） | **0** | GitHub，上次 push 之后 |
| 站点静态内容 | **不为 0，且大部分缺失** | `dtb/index.html`(29.6MB) 与 `story/index.html`(21.6MB) 被 `.gitignore` 排除 → 见 §4 |
| `/etc/rancher/k3s/*`、`/etc/docker/daemon.json`、`jail.local`、`99-sre-lab.conf` | **0** | Ansible 任务里的 `dest`，重跑 playbook 即还原（工具会打印匹配到的任务文件） |
| `/var/lib/rancher`（k3s 状态） | **无上限** | 无备份。配置类可经 ArgoCD 重建，**PV 数据不可** |
| `/etc/letsencrypt`（证书） | **无上限** | 无备份。可重签，但要 80 端口 + 域名解析 + 注意 rate limit |
| `/root/.sre-lab-secrets/alertmanager.yml`（含 SMTP 授权码） | **无上限** | 无备份，且不在库 —— **单点缺失** |
| `vmdata` / `loki-data` / `grafana-data` / `alertmanager-data` | **无上限** | 无备份。面板已 provisioning，但**历史数据与静默状态会丢** |

> 2026-10-19 盘点结果：**✅ 15 / ⚠️ 1 / ❌ 7**，四类备份目录**一个都不存在**。

## 3. 演练方法：影子重建

### 为什么用影子而不是真停

| 方式 | 站点影响 | 错误预算 | 结论可信度 |
|---|---|---|---|
| 真停生产再重建 | 中断 N 分钟 | **消耗**（5 分钟 ≈ 2.3%） | 最高 |
| **影子重建**（新目录 + 新端口 + 新项目名） | **零** | **零** | 略低（端口/证书用了脚手架，需单列） |

选影子的理由：**先把不确定性变成数字，再花预算去买确定性的收益。**

### 三条必须知道的坑

1. **compose 项目名默认取目录名** —— 影子目录若也叫 `nginx` / `observability`，
   `docker compose up` 会直接**接管生产容器**。必须显式 `-p shadow-web` / `-p shadow-obs`。
2. **`container_name` 是全局唯一的** —— 影子 compose 会撞名（`node-exporter` 已存在），
   必须 `sed -i '/container_name:/d'`。
3. **2G 内存跑不了两份全栈** —— 影子只能**逐组件串行**：起一个、验一个、拆一个。

### 脚手架与真实重建的差别（RTO 要注明）

| 项 | 影子演练 | 真实重建 |
|---|---|---|
| 端口 | 改到 8080 / 18428 / 19100 | 直接用 80 / 443 / 8428 |
| 证书 | **不重建**，L1 只验内容层 | 必须重签或从备份恢复 |
| 仓库来源 | GitHub（可用 relay 兜底，**要记录走了哪条**） | 同 |

## 4. 已发现的两个真源漏洞（2026-10-19）

### 4.1 站点 98% 的体积不在任何真源里

```
nginx/html 总 49M，其中：
  dtb/index.html    29.6 MB   ← .gitignore 排除
  story/index.html  21.6 MB   ← .gitignore 排除
  其余 4 个页面 + 2 个图片 + 1 个悬空软链   约 16 KB   ← 在库
```

`.gitignore` 里写着「大体积静态资源：待外置优化，暂不纳入版本控制」。
**后果：从 GitHub 重建出来的站点，首页能开，但 `/dtb/` 与 `/story/` 是 404。**

这条同时否掉了一个更早的判断：**"站点只有 6 个静态文件，用 ConfigMap 就够"** ——
① 文件数不等于字节数（6 个文件 49M）；② ConfigMap 单对象上限 1MB。
→ 站点要进 k8s，仍然需要一条**大文件分发通道**（镜像 / PVC + git-sync），
这件事**不会因为 GitOps 化而消失**。

### 4.2 密钥与数据：既不在库、也无备份

`/root/.sre-lab-secrets/alertmanager.yml` 只有一份，丢了就要重新申请 SMTP 授权码。
`/etc/letsencrypt` 同。这两项是 Week 7-B 的第一优先级。

## 6. 首次实测（2026-10-21）

影子重建，全程未碰 80/443，**错误预算消耗 0**。

| 项 | 表面值 | 内含 `sleep` | 净值 | 拆解 |
|---|---|---|---|---|
| L1 站点（内容） | 11 s | 3 s | **8 s** | 克隆 4 s + 起服务与验证 4 s |
| L2 指标（VM + NE） | 34 s | 25 s | **9 s** | 起服务到 `up=1` |
| 合计 | 45 s | 28 s | **17 s** | |

- **克隆走 GitHub 直连，4 秒**；`relay` 备用路径未触发（`dr.md` 第 3 节写的失败处置没用上）。
- **站点内容验证**：`/` 200、`/404.html` 200、**`/dtb/` 404、`/story/` 404** ——
  与 4.1 的盘点完全一致：那 49 MB 从来没进过仓库，所以"从 GitHub 重建"出来的站是个空壳。
- **`sleep` 必须扣**：`sleep 3` / `sleep 25` 是脚本在等，不是系统在恢复。
  不扣会把 RTO 虚报 **2.6 倍**（45 s vs 17 s），而且这个固定值会在跨次对比时淹没真实变化。

### 6.1 人工决策数：8 条（真实重建 4 条）

**命令条数不可比** —— 同一个 2.1，逐条敲是 9 条、整块粘贴是 1 次，差 9 倍而系统能力没变。
那个数只反映"打字方式"。改数**决策**：只数「换个人来做必须有人告诉他的信息」和
「做错不会自动纠正、必须人判断的地方」，纯搬运（`clone` / `docker run` / `curl`）一律 0 条。

| # | 决策点 | 真实重建需要 |
|---|---|---|
| 1 | 仓库地址 | ✅ |
| 2 | 站点根 `nginx/html` → 容器 `/usr/share/nginx/html` | ✅ |
| 3 | 镜像 `nginx:1.24-alpine` | ✅ |
| 4 | `/dtb/` `/story/` 的 404 是**预期**，不是故障 | ✅ |
| 5 | 8080 避让生产 80/443 | ❌ 影子特有 |
| 6 | 8428 / 9100 已被占，第二份要挪 | ❌ 影子特有 |
| 7 | `container_name` 全局唯一，第二份要删 | ❌ 影子特有 |
| 8 | compose 项目名默认取目录名，要 `-p` 隔离 | ❌ 影子特有 |

**真实重建只要 4 条** → 「重建动作」本身不难。**瓶颈不在操作步数，在内容分发**：
把 GitOps 化当解药，只会把一个"没有内容的站"搬进 k8s。

第 4 条是最贵的一种决策错误 —— 不知道这件事的人看到 404，会去修一个不存在的问题。


## 7. 备份策略：按「能不能再生」分三层（2026-10-21）

### 7.1 为什么不是「压缩 vs 外发」

最初的问法是「`/var/lib/rancher` 1.8 G 该压缩还是外发」。**这个前提是错的** —— 实测：

| 子目录 | 体积 | 性质 | 处置 |
|---|---|---|---|
| `k3s/agent` | **1.5 G** | containerd 镜像与快照层 | 重新 `pull` 即得，**不备** |
| `k3s/data` | **271 M** | k3s 解包的二进制 | 重装即得，**不备** |
| `k3s/server` | **38 M** | 真正的状态 | 备 |

**97% 可再生产。** 而且单节点 k3s 是 **sqlite/kine**，`server/db/etcd` 根本不存在 ——
"只备 etcd 快照"这个方案在这里无从谈起。

### 7.2 三层

| 层 | 内容 | 体积 | 处置 |
|---|---|---|---|
| **A 可再生** | `agent` 1.5 G、`data` 271 M | 1.8 G | 不备，重建 |
| **B 状态** | `state.db` + `tls/token/cred/etc` + `letsencrypt` + `alertmanager.yml` | **3.06 MB（加密前）** | **加密外发** |
| **C 数据** | `vmdata` 63 M（gzip 比率 **0.98**）、`loki-data` 11 M、`grafana-data` 15 M | 89 M | **接受丢失**，缩短保留期 |

C 层认输的理由：**压不动也传不动**。61 MB 走 GitHub 通道（曾实测 8–52 KB/s）要 20 分钟到 2 小时，
换回来的是一批已经过期的指标 —— 为它建的传输管道比数据本身更值钱。

### 7.3 实测数字（2026-10-21）

| 项 | 值 |
|---|---|
| `sqlite3 .backup` 耗时 | **289 ms** |
| 快照 `integrity_check` | **ok** |
| kine 行数（快照时点） | 1436 |
| 打包明文 | **3,204,926 B** |
| 加密后 | 3,204,944 B（AES 基本不增大） |
| 解包文件数 | 76 |

压缩比：

| 对象 | 原始 | 压缩后 | 比率 |
|---|---|---|---|
| `state.db` | 23 MB | **3.3 MB** | **0.15** |
| `server/{tls,token,cred}` | 63 KB | 15.7 KB | 0.25 |
| `/etc/letsencrypt` | 99 KB | ~50 KB | — |
| `vmdata` | 63 MB | **61.3 MB** | **0.98** |

`state.db` 的 23 MB 里**只有 3.96 MB 是真实数据**（82% 是空闲页）。
最大的三个对象是 helm release secret：`gateway-api-crd.v1` 644 K、`argocd.v1` 539 K、
**`argocd.v2` 539 K** —— v1 是升级后的死版本。

### 7.4 四个必须守住的细节

1. **不能 `cp` 正在写的 sqlite。** `state.db` + `-wal` 不是原子快照，拷出来可能是撕裂的。
   必须 `sqlite3 ... ".backup"`。
2. **加密在服务器上做**，不是在目标端做 —— 让"离开这台机器的那一刻"已经是密文。
   算法 `aes-256-cbc + pbkdf2 20 万轮 + sha256`（openssl 1.1.1k 原生，无额外依赖；本机没有 age/gpg）。
3. **口令不落盘。** 手册用 `read -s` 输入、只进环境变量，脚本用 `-pass env:`。
   **丢了就再也解不开** —— 不设"忘记密码"，因为设了就等于留了第二把钥匙。
4. **异地必须真的异地。** 备份留在 `/root/backup` 只是"防手滑"：和数据同盘、同机、同故障域。
   整机释放/欠费/盘坏时淘汰率 100%。

### 7.5 恢复演练验到哪一级

| 级 | 判据 | 状态 |
|---|---|---|
| L1 | 校验和一致 + 能解密 + 能解包 | ✅ 已验 |
| L2 | `integrity_check=ok`、行数 > 0、关键对象在（6 个 namespace、Application hello） | ✅ 已验 |
| L3 | k3s 集群链 `openssl verify` OK；letsencrypt 私钥与证书公钥匹配 | ✅ 已验 |
| L4 | **让一个干净的 k3s 用这份 db 真正起来** | ❌ **未证** |

L4 不做的原因：2 G 机器放不下第二份 k3s，真验要停生产。
**所以「这份备份可用」这句话的上限是 L3。** 谁要在真灾难里用它，必须先接受这一点。

### 7.6 一个容易看错的地方

`restore-state.sh` 会打印 `Application hello 12 条`。**不是 12 个 Application** ——
kine 是 **versioned KV**，同一个 key 每次变更都留一行 revision。
12 条 = 12 个历史版本。判据是「> 0」，不是「== 1」。


### 7.7 一次真实事故：`read -s` 吃掉了整段粘贴（2026-10-22）

**现象**：备份生成了归档，但用"同一个口令"连续几次都 `bad decrypt`。

**排查顺序**：

1. **文件有没有坏** —— 没有。`/tmp/restore-drill` 的副本与 `/root/backup` 原件
   sha256 逐字节相同（`30cfdd6b…`），大小也一致。
2. **脚本有没有问题** —— 没有。用三种口令各跑一遍备份+恢复：
   `testpass123`、27 字节的 shell 元字符、中文（6 字符 / 18 字节），**全部通过**。
3. **那问题就在输入** —— 让用户量一下口令本身：**字符数 496 / 字节数 564**。

**根因**：手册 1.1 的命令块是多行的，页面上还有「复制」按钮：

```bash
read -rsp '备份口令: ' SRE_BACKUP_PASS; echo
export SRE_BACKUP_PASS
bash scripts/backup-state.sh /root/backup
```

整块粘贴时，`read` 把**后面的所有内容**当成口令吃掉了。
而 `read -s` 不回显 —— 用户看到的是"没有任何输入"，以为没粘进去，于是又手输了一遍。
**两次口令必然不同，`bad decrypt` 必然发生。**

**这不是操作失误，是文档设计事故。** 交互式命令不该和后续命令放在同一个可复制块里；
而"看不见输入"这个安全特性，在这种场景下反而成了错误的掩护。

**三道护栏（已加进脚本）**：

| 护栏 | 位置 | 作用 |
|---|---|---|
| 长度 `<6` 或 `>64` 直接拒绝 | `backup-state.sh` 前置 | 496 字节当场被拦，并提示"多半是整块粘贴" |
| **加密后立刻自解一次**（与明文 `cmp`） | `backup-state.sh` 4/5 | **绝不留下打不开的归档**；失败即删产物 |
| `meta` 写 `pass_len`，恢复时先对照 | `restore-state.sh` 2/5 | 解密**前**就说清"当时 11 字节，你输了 21 字节" |

**手动操作的纪律**：含 `read` 的那一行**单独复制、单独执行**，然后手工敲口令。
不要在同一个块里连着做。

**判据上的收获**：`bad decrypt` 是一个**没有指向性的错误** ——
它同样可能来自口令错、文件坏、参数不一致。把它翻译成
「长度不符：当时 N 字节，你输入 M 字节」才是可行动的判据。
