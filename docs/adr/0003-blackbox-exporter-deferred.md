# ADR 0003：暂不部署 blackbox-exporter，先清除死变量

- **日期**：2026-10-14
- **状态**：已采纳（2026-10-19 解除暂缓 —— 落地与消费方同批提交，见 [ADR 0005](0005-blackbox-on-docker-compose.md)）
- **相关**：[methodology ⑧](../methodology.md)（死变量会误导人以为功能已存在）

## 背景

`observability/.env` 里长期躺着一行 `BB_VER=v0.29.0`，但 `docker-compose.yml` 里
**没有任何 service 引用它** —— 一行典型的死变量。

危害不是"多了一行没用"，而是**误导**：看到 `.env` 里有版本号，很容易以为
blackbox-exporter 已经纳入管理。10-09 那次告警链路故障里，`AM_VER` 就是这样躺了很久，
而 alertmanager 实际**根本没定义**（见 [2026-10-09](../incidents/2026-10-09-alert-chain-silent.md)）。

## 决策

**删除 `BB_VER`，本轮不部署 blackbox-exporter。** 理由：

1. **没有消费方。** blackbox-exporter 的用途是外部可用性拨测（HTTP / TCP / ICMP）。
   当前 4 条告警规则全部基于 `up{job="node"}`（内部指标），**没有任何规则依赖 blackbox**。
   现在加它只是"多一个容器"，不产生任何闭环价值。
2. **它的用武之地是 Week 5-6（SLO 与告警治理）。** 那时才会有可用性 SLI、拨测成功率这类规则消费它。
   **功能应与消费方同批引入** —— 否则引入当天它就是新的死变量。
3. **自拨公网入口存在回环 NAT（hairpin NAT）不确定性。**
   从 ECS 本机访问自己的公网 IP，在阿里云 NAT 策略下未必可达。
   真要做外部探测，得先做一次受控实验确认这条路径通不通 ——
   那是独立任务，不该塞进本轮「收口」。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| 直接部署，保留 `BB_VER` | 没有规则消费它，收益为零；且未先验证 hairpin NAT，可能装完才发现探不到自己 |
| 保留 `BB_VER`，只在文档写"未部署" | 死变量仍在，误导性没消除 —— ⑧ 针对的正是这种"看着像已存在" |
| 把 `BB_VER` 换成 `# TODO` 注释 | `.env` 是版本账本，不是待办清单；注释同样会随人走而漂移 |

## 后果

- `.env` 现在**每一项都被 service 引用**（`VM_VER` / `NE_VER` / `AM_VER`），
  因此「`.env` 里的变量数 == compose 里被引用的变量数」可以直接当一致性判据。
- 引入时机记在 [baseline](../baseline.md) 的「六、待补基线」。
- 将来部署时，**必须与消费它的告警规则同批提交**，并先验证公网拨测路径。
